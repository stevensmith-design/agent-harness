## Findings

**R11 — kit defect.** `harness-build`'s description guards its entry by enumerating
verbs: *"a request to create, build or set up a harness goes to harness-scope
first"*. The request said **copy** and **instantiate**, neither of which is on the
list, so the guard did not fire and the judge routed to build with no architecture
document in existence — the same shape as the original entry defect. A verb list
is a denylist, and a denylist of phrasings is a guard that fails on the next
phrasing. The guard belongs on the **condition** (does an agreed architecture
document exist?) rather than on the words.

The misroute is recoverable — `harness-build`'s own precondition 1 stops and sends
the user to scope — but routing that depends on the skill catching it after the
fact is not routing, and the person has already been told a different skill owns
their request.

**R05 — case defect, and the more useful of the two.** The expected claimant was
wrong. *"I want Claude to always follow our brand rules when it writes for us"* is
a request for brand guidelines, not for a harness engagement, and the judge said so
by name. The case over-claimed on the kit's behalf — which is precisely the failure
R17–R20 exist to catch, committed by the author of R17–R20. Amended: expected
`none`, and the case kept, because a case the kit should NOT win is worth more than
one it wins easily.

**Methodology — the judges were not isolated.** A subagent inherits the host
session's skill catalogue, so every judge here could see unrelated skills
(brand-voice, design, product-management) alongside the kit's three. R05's
reasoning names one. This makes the run *more* realistic than the procedure
described — real competition, not a three-way choice — but it is not what
`../README.md` said would happen, and `../cases.md` claimed "only three skills
compete", which was false for this run. Both files corrected. The contamination
runs in the direction of difficulty, not leniency, so the 18 passes stand.
