# Install

Two trees, and keeping them straight is the whole of it.

- **The kit** — this directory. It builds harnesses. It is never copied into your work.
- **The harness** — what `core/` becomes once it is copied into a project and filled in.

The kit stays put. Harnesses are what travel.

---

## 1 · Put the kit somewhere stable

Anywhere you will not move it. It is read, not run in place.

```
~/harness-kit/          # or wherever
```

## 2 · Make the skills invokable

The three skills are plain `SKILL.md` files. Nothing loads them until they sit where your tool looks.

**Claude Code — for every project:**

```bash
mkdir -p ~/.claude/skills
cp -R ~/harness-kit/skills/harness-scope  ~/.claude/skills/
cp -R ~/harness-kit/skills/harness-build  ~/.claude/skills/
cp -R ~/harness-kit/skills/harness-audit ~/.claude/skills/
```

**Claude Code — one project only:** same, into that project's `.claude/skills/`.

**Cursor:** `~/.cursor/skills/`.

**Claude Desktop / Cowork — no filesystem, no shell.** Skills are saved to your account, not copied
into a directory, and there is no profile to export a variable from. Save each of the three skill
files through the app; then **connect the folder the kit lives in** as session context. That
connected folder replaces `$HARNESS_KIT` entirely — see below.

**Anything else:** point your tool's skill loader at `~/harness-kit/skills/`. The files are host-agnostic markdown; only the loading path differs.

> **Why the kit's skills sit at `skills/` and not `.claude/skills/`:** the kit is a
> library you copy *from*, not a project an agent reads. A `.claude/` directory here
> would claim one host for a tree that serves several. Harnesses the kit *builds* are
> different — there, procedures are canonical and `.claude/skills/` holds generated
> pointers, regenerated by `./scripts/sync-skills.sh`.

### Tell the skills where the kit is

Each skill opens with a **required reading** table naming `ANATOMY.md`, `LADDER.md` and the packs. Once the skill is installed, **those relative paths no longer resolve** — the skill is a lone file, and nothing records where the kit lives.

**Three ways, in the order a skill should try them:**

1. **A connected folder** containing `ANATOMY.md`, `LADDER.md`, `core/` and `packs/`. This is how
   Claude Desktop and Cowork work, and it needs no configuration — the kit is simply one of the
   folders attached to the session. Look before asking.
2. **`$HARNESS_KIT`**, where there is a shell to export it from:

   ```bash
   export HARNESS_KIT=~/harness-kit
   ```

3. **Ask.** If neither resolves, ask for the path before reading further, rather than proceeding
   without the theory — which is the re-explaining this kit exists to remove.

**Never assume an environment variable exists.** A skill written around `$HARNESS_KIT` alone works
in Claude Code and silently has no theory in Claude Desktop, where nothing can set one — and a
harness designed without the theory is the exact failure the required-reading table exists to
prevent.

> **Copies drift.** These are copies, and nothing syncs them. When you change a skill, change it in the kit and copy again — or symlink instead, and accept that a moved kit breaks the link.

**They also work with nothing installed.** `harness-scope` and `harness-build` are procedures; you can open the file and follow it. Installing makes them invokable, not functional.

## 3 · Know which directory you are in

`harness-build` reads from the kit and writes to the target. They are different trees, and the skill says which is which at each phase:

| Phase | Reads from | Writes to |
|---|---|---|
| 1 Inventory | the target | nothing |
| 2 Instantiate | **the kit** (`core/`) | the target root |
| 3–6 | the target | the target |
| 5 Pack | **the kit** (`packs/`) | the target |

Concretely, Phase 2 is one command, run from the kit:

```bash
~/harness-kit/install.sh /path/to/target-project
```

**It never overwrites anything.** It lists collisions, asks, copies only what does not already exist, and stages colliding files at `.harness-incoming/` with a per-file note on how to merge each one.

That matters because a raw `cp -R core/. .` silently replaces a project's existing `README.md`, `AGENTS.md`, `.gitignore` and `.claude/settings.json` — the four files most likely to already be there, and the ones Phase 1 explicitly says get *merged, never silently overwritten*. On a git substrate that is recoverable. In a workspace it is not.

**Root only.** The installer refuses to install below a repository root, because surface patterns and the harness/content split gate both resolve from the harness root: a subdirectory install goes green while being unable to classify the work it governs. That is a false green inside the machinery that exists to prevent false greens.

Then verify before doing anything else:

```bash
./scripts/doctor.sh          # is the harness intact?
./scripts/gate-selftest.sh   # can every gate still fail?
```

## 4 · What is NOT wired yet

Say this out loud rather than discovering it mid-run:

**The packs are documents, not file sets.** `harness-build` Phase 5 says "apply the pack from `packs/`". Today that means *read it and make the decisions it names* — there are no files to copy. The dev pack points at `universal/`, a reference implementation that ships alongside the kit; the design and business-development packs are complete as documents; the two sketches are starting hypotheses.

For a first run this matters less than it sounds: the kit's own advice is **minimum viable configuration**. What you need is the work, the foundations, one surface, and the prime directive. The pack is guidance on top of that, not a prerequisite.

**No CI ships.** A repository-substrate harness at L2 needs `./scripts/check.sh` wired into its own CI. Write it; nothing generates it.

**Hooks are Claude Code only.** `.claude/settings.json` wires session state,
finish-time checking, sensitive-read blocking, and the rule that the agent does
not install third-party code. Other hosts still get the repository/workspace
gates and constitution, but not these pre-tool controls; render equivalent
runtime hooks before claiming parity there.

## 5 · If this is a trial

Open [`TRIAL.md`](TRIAL.md) **before you start** and fill it as you go. Its most important section is the steps you skipped and why — which is exactly the part people leave out when writing up afterwards.

## 5 · First run

Follow `core/README.md` §First steps, or invoke `harness-scope`. It gathers context, then tells you whether it thinks this work needs a harness. That is a recommendation — the call is yours.

**Then put one real piece of work through it.** A harness that has never carried work is a rehearsal, and that is where this stalls more often than anywhere else.
