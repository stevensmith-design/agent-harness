# 単体プロンプト (スキルを使わない場合)

Claude Code のスキルを入れずに、Claude / codex / Cursor などのエージェントにそのまま貼って使うプロンプトです。`{{ }}` の部分を書き換えてください。スキル同梱の `scripts/render.py` を使える環境なら「出力」の (B) を、使えないなら (A) を残してください。

---

あなたは、このリポジトリのアプリケーションについて (1) システムの把握と (2) 外部サービスの利用規約・API ポリシーとの突き合わせを行い、レポートにまとめます。法的判断ではなく、規約の文面と実装の突き合わせとして書いてください。

守ること:
- コードを変更しない。静的に読むのが既定。アプリを起動するのは、隔離環境・架空データ・外部送信の無効化が揃うときだけ
- 秘密情報 (API キー、トークン、`.env` の実値) と実在の個人データをレポートに書かない。例示は架空の値にする
- 規約は公式ページの原文で判定する。取得できなかった規約に依存する項目は「未確認」にする
- 範囲は外部サービスの契約・規約・ポリシー・ガイドラインと提供データのライセンス。法令や OSS ライセンスは、依頼があるか外部サービスの規約が求める場合だけ扱い、根拠の種類を書く

- 対象: {{リポジトリのパス}} ({{ブランチ}} @ {{コミット}})
- 対象の外部サービス: アプリが関わるものすべて。特に見てほしいもの: {{例: 決済、生成 AI、地図}} (挙げたものに限らない)
- 依頼者の疑問: {{例: 「Google Maps API のレスポンスを DB にもキャッシュにも保存していないか」}}
- 出力先: {{例: ../audit-20261016/}}

## Phase 1: システムを把握する

1. README、`.env.example`、パッケージ定義、インフラ定義 (Dockerfile、Terraform、CI)、DB スキーマとマイグレーション、エントリポイント (ルート、API、Webhook、バッチ) を読む。
2. アプリが関わる外部サービスを全部列挙する。分類 (メッセージング、地図、生成 AI、決済、認証・ソーシャルログイン、メール・SMS、プッシュ通知、分析・計測・広告、エラー監視・ログ、ストレージ・CDN・ホスティング、アプリストア、外部データ API・提供データ、埋め込み、スクレイピング先) を 1 つずつ確かめ、サーバー・フロントエンド・モバイル・インフラ・CI のすべてから探す (SDK、HTTP、埋め込みタグ、環境変数)。見つけたサービスごとに「使っている API、呼び出し箇所 (`file:line`)、送るもの、受け取るもの、保存先と期間、表示先、認証」を表にする。送るものに他社から受け取ったデータ (チャット本文、ユーザー ID、他 API の応答) が混ざっていないかを必ず書く。
3. DB の列、JSON 列、ログ、キャッシュ、エクスポートに、どの外部サービス由来のデータが残るかを洗う。削除の仕組み (退会、保持期間、送信取消) の有無も書く。
4. 利用者の操作ごとの経路 (例: チャットで相談、アプリ内で詳細を見る、定期配信、日次バッチ、管理画面) を、入口から外部サービスと保存先を経て出口まで書く。
5. 構成図 (ASCII か Mermaid) と、主要な経路のシーケンス図を作る。図の中は ASCII、日本語の説明は凡例に。

## Phase 2: 規約の原文を集める

各サービスについて、まず適用される規約を特定する (契約主体、オンライン規約か個別契約か、プラン、地域、API の世代、施行日。分からなければ前提として書く)。そのうえで、基本契約、サービス固有規約、データの扱い、利用ポリシー、API ごとのポリシー、開発ガイドライン、ロゴ・帰属表示の規定、ストアのポリシー、データのライセンスを公式ページから取得する。URL、版 (Last modified)、取得日、判定に使う条項の短い原文引用を残す。取得できなかった文書は「未取得」と書く。公開規約の無いデータ提供元は「個別契約が根拠」として確認事項に回す。

## Phase 3: 突き合わせる

全サービスに次の観点を当てる。

1. 他社から受け取ったデータを別の外部サービスに送っていないか (送り元の規約の論点になることが多い)
2. 応答の保存が、規約の許すキャッシュ範囲 (識別子だけ、期限付きの座標だけ、など) に収まるか。ログや JSON 列も含む
3. 応答から計算した値 (派生値) をどこに使い、出し、残すか
4. 表示先の制限、帰属表示 (寸法、省略の可否)、改変の禁止
5. 利用者への通知と同意、プライバシーポリシーへの記載、利用開始前に読めるか
6. 退会・削除・送信取消
7. 年齢制限、禁止用途 (負荷試験、スクレイピング、学習、広告媒体化)、鍵の管理
8. データ提供元との契約で許されていない加工・配信
9. 分析・広告・エラー監視に個人情報や他社 API の応答を送っていないか
10. 決済の扱い、アプリストアの審査ガイドラインとプライバシー申告が実装と一致するか

判定は 4 段階で、重さではなく分かっていることの状態で選ぶ: 違反の疑い (文面と実装が明らかに食い違い、例外に当たる事実も無いと確かめた) / 要判断 (事実は分かったが、読み方・契約・運用次第。推奨止まりも含む) / 未確認 (判定に要る事実や規約の原文が無い) / 適合 (事実と規約の両方を確認できた)。証拠不足を適合にしない。各項目に ID (サービスの頭文字 + 連番)、どの規約の論点か、根拠の種類、条項と引用と出典、`file:line`、対応案を付ける。項目は「同じ義務・同じ是正」で 1 つにし、同じ事実でも別の規約の別の義務なら別項目にして関連付ける。

注意: 「保存していない」と書く前に、ログ・イベントの JSON・エクスポートを grep して反証を探す。「自社アプリだから表示可」「委託先と整理すれば可」「加工すれば対象外」のような前提付きの判定は、前提を書いて「要判断」にする。

## Phase 4: 検証する

違反の疑いと要判断の全件について `file:line` を開き直して確かめる。「保存していない」「送っていない」と書いた項目は反証を探す grep を打つ。同じ義務の言い換えを統合する。

## Phase 5: 整理する

1. 経路ごとの具体例: 架空の操作 1 本を通し、各ステップで動くデータ (JSON、保存先の列、プロンプトの抜粋) を実物の形で書き、そのステップで関わる項目を `[違反] L-04` `[要判断] G-04` のように添える
2. 経路 x 規約 の一覧表
3. 対応方針: 違反の疑い・要判断・未確認の全項目を次のどれか 1 つに入れ、カテゴリごとに短い箇条書きで方針を書く。A 文書の変更で済む (工数小) / B 年齢などの利用条件チェック (工数小) / C ロジック変更 (工数中) / D 機能実装 (工数中) / E 設計の見直し (工数大) / F 契約・設定・相手先の確認待ち
4. サービス別の全項目
5. コードの外で確認が要ること
6. 参照した規約 (名称、URL、版、取得日)
7. 付録: 依頼者の疑問への直接の回答

## 出力

(A) Markdown 1 ファイル: 上の 1〜7 の順で `{{出力先}}/terms-review.md` に書く。Phase 1 の成果は冒頭に「システム概要」として置く。

(B) JSON + 描画: 配布物の `app-terms-audit/references/schema.md` の形で `{{出力先}}/report.json` を書き、同じ配布物の `scripts/render.py` で描く。この 2 ファイルが手元に無い場合は (A) にする。

```bash
python3 {{app-terms-audit の場所}}/scripts/render.py {{出力先}}/report.json --check
python3 {{app-terms-audit の場所}}/scripts/render.py {{出力先}}/report.json --format both --out {{出力先}}
```

最後に、判定の件数、違反の疑いの一覧、依頼者の疑問への答え、コードの外で確認が要ることを短く報告してください。
