## 守ること

- コードを変更しない。アプリを起動しない (静的に読む)。
- 秘密情報 (API キー、トークン、`.env` の実値) と実在の個人データを出力に書かない。例示は架空の値にする。
- 規約は公式ページの原文で判定する。取得できなかった規約に依存する項目は「未確認」にする。
- 公開中の最新版が対象に適用されるとは限らない。契約主体、プラン、地域、API の世代、個別契約が分からないものは前提として書く。

## 進め方

1. コードを読み、アプリが関わる外部サービスを全部列挙する。メッセージング、地図、生成 AI、決済、認証・ソーシャルログイン、メール・SMS、プッシュ通知、分析・計測・広告、エラー監視、ストレージ・CDN・ホスティング、アプリストア、外部データ API・提供データ、埋め込み、スクレイピング先などを、サーバー・フロントエンド・モバイル・インフラ・CI のすべてから探す (SDK、HTTP、Webhook、埋め込みタグ、環境変数)。各サービスについて、送るもの、受け取るもの、保存先と期間 (DB、ログ、JSON 列、エクスポート)、表示先を `file:line` 付きで押さえる。
2. 各サービスの最新の規約を公式ページから取得する。基本契約だけでなく、サービス固有規約、データの扱い、利用ポリシー、API ごとのポリシー、開発ガイドライン、ロゴ・帰属表示の規定まで当たる。取得日・URL・版を残す。
3. 次の観点を全サービスに当てる。
   - 他社から受け取ったデータ (チャット本文、ユーザー ID、他 API の応答) を別の外部サービスに送っていないか
   - 応答や応答から計算した値 (派生値) を、規約が許す範囲を超えて保存・表示・配信していないか
   - 帰属表示、改変の禁止、表示先の制限
   - 利用者への通知・同意、プライバシーポリシーへの記載、利用開始前に読めるか
   - 退会・削除・送信取消への対応
   - 年齢制限、禁止用途、鍵の管理
   - データ提供元との契約で許されていない加工・配信
   - 分析・広告・エラー監視に個人情報や他社 API の応答を送っていないか
   - 決済、アプリストアの審査ガイドラインとプライバシー申告
4. 「違反の疑い」「要判断」「未確認」「適合」の 4 段階で判定する。判定は重さではなく分かっていることの状態で選ぶ。証拠が足りなければ「未確認」、読み方や契約で結論が変わるなら「要判断」(分かれ目を書く)、事実と規約の両方を確認できたときだけ「適合」。「違反の疑い」は、例外に当たる事実が無いことまで確かめたときだけ。
5. 項目は「同じ義務・同じ是正」で 1 つにする。同じ事実でも別の規約の別の義務なら別項目にする。

1. 判定一覧の表: ID (01 から連番)、サービス、規約の条項と短い原文引用と URL、該当する実装 (`file:line`)、何が起き得るか、判定、推奨対応
2. 依頼者の疑問への直接の回答 (下に疑問があれば)
3. コードの外で確認が要ること
4. 確認した規約の一覧 (名称、URL、取得日、版)

結論を先に、1 文 1 論点で書いてください。法的判断ではなく、規約の文面と実装の突き合わせとして書いてください。
