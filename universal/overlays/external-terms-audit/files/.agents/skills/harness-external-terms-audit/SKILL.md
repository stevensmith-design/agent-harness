# harness-external-terms-audit: システム把握と外部サービス利用規約の監査

アプリのコードを根拠に「何が・どこから・どこへ流れ、どこに残るか」を把握し、その流れを外部サービスの規約原文と突き合わせて、違反になり得る箇所を洗い出す。成果物は 1 つの JSON (`report.json`) にまとめ、同梱の `scripts/render.py` で Markdown か HTML (または両方) に描く。

このスキルは法的判断をしない。規約の文面と実装の突き合わせを行い、判断が要る箇所を法務や相手先に渡せる形に整理する。

**範囲**: 外部サービスの契約・規約・ポリシー・ガイドラインと、提供データのライセンス。法令 (個人情報保護法、特商法など) や PCI DSS は、外部サービスの規約がそれを求めている場合か、依頼者が求めた場合だけ扱い、扱うときは根拠の種類を「法令」と明記する。OSS ライセンスの包括監査は既定で対象外 (外部サービスの SDK や配布物の条件に関わる範囲だけ見る)。一般的なセキュリティの改善提案は判定表に混ぜない。

**パスの決まり**: このファイルがあるディレクトリを `<skill>` と呼ぶ。スクリプトやプロンプトは `<skill>/scripts/render.py` のように、スキルの場所を基準にした絶対パスで参照する (作業ディレクトリは対象リポジトリなので、相対パスでは見つからない)。対象リポジトリ、スキル、出力先の 3 つを混同しない。

| 1 | システムを把握する | 構成図、外部サービス台帳、データの保存先、ユーザーフロー | [references/phase1-survey.md](references/phase1-survey.md) |
| 2 | 規約の原文を集める | 規約ごとの URL・版・取得日・原文引用 | [references/phase2-terms.md](references/phase2-terms.md) |

サービスの分類ごとの観点と、個別サービスで実際に問題になった論点は [references/pitfalls.md](references/pitfalls.md) にある。出発点として使い、必ず原文で裏を取る。`report.json` の形は [references/schema.md](references/schema.md)、最小の例は [examples/report.example.json](examples/report.example.json)。

Phase 1 だけ (システム把握だけ) の依頼なら Phase 2 以降を飛ばし、`report.json` の `survey` だけを書いて描く。

## Phase 0: 範囲を決める

依頼から次を読み取り、分からなければ妥当な既定値で進めて、レポートの冒頭に前提として書く。質問で止めるのは、対象リポジトリが特定できないときだけにする。

- **対象**: リポジトリのパス、ブランチ、コミット (`git rev-parse HEAD`)。コミットは必ず記録する。
- **監査モード**: インシデント対応、クライアント・法務向け報告、全件調査は `formal`。特定機能・特定サービスの確認は `focused`。指定がなければ依頼の範囲から選び、冒頭に記録する。`focused` を全件調査へ勝手に広げない。
- **対象サービス**: アプリが関わる外部サービスすべて。依頼に名前が出たものに限らない。サーバー側の API 呼び出しだけでなく、フロントエンドやモバイルアプリに埋め込んだ SDK・タグ、ログイン手段、配信基盤、アプリストア、データ提供元、インフラ (クラウド、CDN、ホスティング) も含める。分類と見つけ方は [references/phase1-survey.md](references/phase1-survey.md) の「外部サービスの分類」
- **依頼者の関心事**: 「レスポンスを DB に保存していないか」のような具体的な疑問が書かれていたら、原文のまま `questions` に控え、最後に直接答える。
- **出力形式**: `md` / `html` / `both`。指定が無ければ `md`。HTML は 1 ファイルで完結 (CSS 内蔵、外部依存なし。Mermaid 図があるときだけ CDN を読む)。
- **出力先**: 指定が無ければ対象リポジトリの外 (例: `../audit-YYYYMMDD/`)。対象リポジトリにファイルを書かない。

## 守ること

1. **コードを変更しない。静的に読むのが既定。** アプリを起動するのは、隔離した環境・架空のデータ・外部送信の無効化 (課金 API、メール、プッシュ、分析、ジョブ) が揃うときだけ。揃わなければ起動せず、画面などは「未確認」として進める。
2. **事実には `file:line` を付ける。** 推測で書いた箇所は「未確認」と明記する。
3. **規約は毎回原文を取りに行き、適用されるものを選ぶ。** 記憶や pitfalls.md の要約で判定しない。公開中の最新版が対象の契約に適用されるとは限らないので、契約主体、地域、プラン、API の世代、個別契約による上書き、施行日を確かめる (分からなければ前提として書き、確認事項に回す)。URL、版、取得日、短い原文引用を残す。取れなかった規約は「未取得」と書いて判定を「未確認」にする。
4. **範囲を守ってから絞る。** `formal` では Phase 1 の台帳に見つかった外部サービスを全部載せる。監査の深さはリスク (利用者データが流れるか、他社データを再配布するか、課金や審査に関わるか) で濃淡を付けてよいが、載せないサービスを作らない。`focused` では指定されたサービスと、そのデータの送り元・送り先だけを追い、確認した範囲と対象外を明記する。
5. **どちらの規約の話かを分ける。** 「A 社のデータを B 社に送る」は A 社の規約の論点であることが多い。finding ごとに `owner` (どの規約の論点か) を持たせる。
6. **断定しすぎない。** 「この整理なら足りる」「顧客の所有物だから可」のような前提を置いた判定は、前提を明記して「要判断」にする。前提の確認は `checks` に回す。
7. **派生値を見落とさない。** API の応答そのものだけでなく、応答から計算した値 (座標から出した最寄り駅、営業時間で絞った結果、生成 AI の出力に混ざった値) がどこに出てどこに残るかを追う。
8. **保存とログを見落とさない。** DB の列だけでなく、送信ログ、イベントログ、ジョブのエラーログ、エクスポート、キャッシュ、バックアップ、ブラウザや端末内の保存 (localStorage、IndexedDB、Service Worker のキャッシュ、端末 DB、ファイル) に残るものも見る。
9. **検証を監査の重さに合わせる。** `formal` は別のエージェント (codex など) に同じ依頼を独立にさせ、Phase 4 の手順で照合する。`focused` は Phase 4 の自己再検証を必須とし、違反の疑い (`V`)・要判断 (`J`) がある、または依頼者が求めた場合だけ独立レビューを追加する。照合で誤りが見つかったら訂正し、その事実をレポートに残す。別のエージェントが使えない環境では、自己再検証だけ行い、独立レビューが無いことを明記する。
10. **秘密情報を書かない。** API キー、トークン、個人データの実値はレポートに載せない。例示は架空の値にする。

## 描画

```bash
python3 <skill>/scripts/render.py <出力先>/report.json --check
python3 <skill>/scripts/render.py <出力先>/report.json --format md   --out <出力先>
python3 <skill>/scripts/render.py <出力先>/report.json --format html --out <出力先>
python3 <skill>/scripts/render.py <出力先>/report.json --format both --out <出力先>
```

`render.py` は Python 3.9 以上の標準ライブラリだけで動く。`--check` は構造と参照を検査し、エラー (必須キー欠落、ID の重複、参照切れ) があると描画しない。警告 (カテゴリ漏れなど) は描画を止めないが、直してから渡す。HTML を描いたらブラウザかヘッドレス Chrome で開いて、崩れが無いかを目で確認する。

## 報告

作業の最後に、依頼者に次を短く伝える。

- 判定の件数 (違反の疑い / 要判断 / 未確認 / 適合)
- 違反の疑いの一覧 (1 行ずつ)
- 依頼者の疑問への直接の答え
- 独立レビューとの照合で変わった点 (訂正があれば必ず)
- 出力ファイルのパス
- コードの外で確認が要ること (契約、コンソール設定、相手先への質問)
