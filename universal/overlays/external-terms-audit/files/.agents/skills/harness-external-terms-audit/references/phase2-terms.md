# Phase 2: 規約の原文を集める

## 集める文書の種類

Phase 1 の台帳にある外部サービスすべてについて、次の層を当たる。上位の契約だけ見て下位のポリシーを落とすのが一番多い漏れ。

| 層 | 例 |
|---|---|
| 基本契約 | 各サービスの Terms of Service (例: Google Maps Platform、Google Cloud、LINE 開発者契約、OpenAI、Stripe Services Agreement、Twilio、Firebase) |
| サービス固有規約 | Maps Service Specific Terms、Cloud Service Specific Terms (生成 AI の章)、LINE 公式アカウント API 利用規約 |
| データの扱い | Data Processing Addendum (DPA)、ユーザーデータポリシー、プラットフォームのプライバシー要件 (例: LINE ユーザーデータポリシー、Google Analytics の PII 禁止) |
| 利用ポリシー | Acceptable Use Policy、禁止用途ポリシー (例: Generative AI Prohibited Use Policy、OpenAI Usage Policies、Stripe の制限業種、メール配信サービスの送信ポリシー) |
| API ごとのポリシーページ | API 単位の利用条件・帰属表示・キャッシュ規定 (例: Places API Policies、各社のレート制限とキャッシュの規定) |
| 開発ガイドライン | 各社の開発者ガイドライン (例: Messaging API / LIFF 開発ガイドライン、Sign in with Apple のガイドライン) |
| ブランド・表示 | ロゴガイドライン、帰属表示の寸法 |
| ストア・配布のポリシー | App Store Review Guidelines、Google Play デベロッパーポリシー (モバイルアプリの場合) |
| データのライセンス | オープンデータの利用規約 (CC BY など)、出典表示の要件 |
| 個別契約 | 発注書、データ提供契約、API 利用契約 (リポジトリに無ければ「未確認」として `checks` に回す) |

公開規約が無い提供元 (データ提供元、受託開発先の API) は「個別契約が根拠」と書き、契約の有無と中身を確認事項にする。

## 適用される規約を選ぶ

公開中の最新ページが、対象の契約に適用される規約とは限らない。サービスごとに次を確かめ、台帳に書く。分からない項目は前提として書き、`checks` に回す。

- 契約主体 (誰の名義のアカウントか。受託開発なら発注者か受注者か)
- 契約の種類 (オンライン規約か、個別契約・販売代理店経由か。個別契約は公開規約を上書きすることがある)
- 請求先の地域、プラン (無料か有料か。無料枠でデータの扱いが変わるサービスがある)
- API の世代と使っている機能 (旧版と新版で規約が違う、特定の機能だけ追加条件がある)
- 施行日 (改定の直前直後なら、どちらが適用されるか)

## 取り方

- 公式ページを WebFetch か `curl` で取得する。取得日、URL、ページ上の版表記 (Last modified、改定日) を控える
- 要約ツール経由でしか読めなかったものは「要約経由」と印を付け、判定の根拠には原文を引ける条項を優先する
- 引用は短く (1〜3 文)、条番号付きで。判定の根拠に使う文は必ず原文で残す
- 改定が近い場合は旧版も控える (例: 直前の版のアーカイブ URL)

## 書き出し

調査メモは Markdown で残す (例: `terms/<service>.md`)。メモには条番号、原文引用、自分の読み方 (要約) を分けて書く。`report.json` の `sources` には、`id`・名前・URL・版 (施行日)・取得日を入れ、各 finding の `refs` からその `id` を指して、判定から出典に辿れるようにする。

## 外部エージェントに任せるとき

規約集めはサービスごとに独立しているので、並行に分けやすい。任せるときの依頼文には次を入れる。

- 対象サービスと API の一覧 (Phase 1 の台帳から)
- 「原文の条番号と短い引用を必ず残す。要約だけで判定しない」
- 「取得日と版を残す。取れなかった文書は取れなかったと書く」
- 「このアプリの使い方 (送るもの・保存・表示先) に関係する条項を優先する」
