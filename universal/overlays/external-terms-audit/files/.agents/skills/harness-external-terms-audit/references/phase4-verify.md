# Phase 4: 検証する

## 1. 自分で裏を取る

- 違反の疑い (`V`) と要判断 (`J`) の全件について、`fact` に書いた `file:line` を開き直して、書いた通りか確かめる
- 「保存していない」「送っていない」「表示していない」と書いた項目は、反証を探す grep を 1 回ずつ打つ (列名、JSON のキー、ログ出力、エクスポート)
- 同じ義務・同じ是正を言い換えた項目を統合する。統合した側の ID は欠番にし、残す側の `clause` と `fact` に吸収する。別の義務なら統合せず `related` で結ぶ (Phase 3 の「項目の単位」)

## 2. 必要なときに独立レビューを入れる

`formal` 監査ではこの手順を行う。`focused` 監査では、違反の疑い
(`V`)・要判断 (`J`) がある場合、または依頼者が求めた場合に行う。
それ以外の `focused` 監査は「1. 自分で裏を取る」を完了すればよく、
独立レビューを監査の件数を増やすための儀式にしない。

自分のレビューを見せずに、別のエージェントに同じ依頼をする。自分の結論を渡すと追認されやすい。

依頼文は `<skill>/prompts/cross-review-prompt.md` を元に、末尾の入力欄 (対象、コミット、依頼者の疑問、Phase 1 で見つけた外部サービスの一覧) を埋めて作る。自分の判定は渡さない。

codex CLI の例 (読み取り専用、web 検索あり):

```bash
codex --search exec -s read-only -C <対象リポジトリ> --skip-git-repo-check \
  -o <出力先>/cross-review.md "$(cat <出力先>/cross-review-prompt.filled.md)" < /dev/null
```

`--search` は `exec` より前に置く。`< /dev/null` を付けないと、バックグラウンド実行時に標準入力の待ちで止まる。Claude Code のサブエージェントに頼む場合も、同じ依頼文を渡す。

別のエージェントも CLI も使えない環境では、独立レビューを省き、「1. 自分で裏を取る」をもう一周してから進む。レポートの `cross_review.reviewer` に「独立レビューなし (自己再検証のみ)」と書く。

## 3. 照合する

独立レビューの各項目を、自分の findings と 1 件ずつ対応付けて `cross_review` に入れる。

| 一致 | 意味 | やること |
|---|---|---|
| 同 | 同じ判定 | そのまま |
| 強 | 相手の方が重い | 下の再照合をして、判定を上げるか、保つ理由を書く |
| 弱 | 相手の方が軽い | 下の再照合をして、判定を下げるか、保つ理由を書く |
| 新 | 自分に無い指摘 | コードで確かめ、正しければ新しい項目として足す |
| 否 | 採用しない | 理由を書く |

「強」「弱」のどちらでも、**コード (事実)、規約の原文、適用条件 (契約主体、プラン、例外の有無)** の 3 つを再照合し、上げる・下げるの両方を許す。食い違いの原因が規約の読み方の違いなら、判定を `J` にして両方の読み方を `action` に併記する。

相手の指摘で自分の誤りが分かったら、該当項目を直し、レポート本文 (依頼者への回答を含む) も直し、`cross_review` のメモに「初版の記述は誤り」と残す。訂正を隠さない。

自分にあって相手に無い項目は `cross_review.missing` に ID を並べる。
