# Phase 3: 突き合わせて項目を立てる

## 観点チェックリスト

台帳にある外部サービスすべてに、次の観点を 1 つずつ当てる。分類ごとの重点は [pitfalls.md](pitfalls.md) の「分類ごとの観点」を使う。該当が無い観点も「確認した」ことが分かるように、適合として残すか、メモに書く。

1. **入れるもの**: 他社から受け取ったデータ (チャット本文、ユーザー ID、他 API の応答) を、このサービスに送っていないか。送るなら、元の会社の規約が第三者提供を許すか
2. **保存**: 応答をどこに、どれだけ残すか。規約が許すキャッシュの範囲 (識別子だけ、期限付きの座標だけ、など) に収まるか。ログ・JSON 列・エクスポートも含む
3. **派生値**: 応答から計算した値 (距離、最寄り駅、絞り込み結果、生成文) をどこに使い、どこに出し、どこに残すか
4. **表示先**: 規約が許す場所 (自社アプリ内、利用者本人の画面) の外に出していないか。チャットのメッセージ、メール、他社アプリ、公開ページ
5. **帰属表示**: ロゴ、クレジット、著者名、リンクの要件。寸法と省略の可否まで見る
6. **改変**: 応答の値を書き換えて、そのサービスの表示欄に出していないか (URL の差し替え、並べ替えの改ざん)
7. **利用者への通知と同意**: プライバシーポリシー、利用規約にサービス名・送る項目・保存期間を書いているか。利用開始前に読めるか
8. **退会・削除・送信取消**: 利用者が辞めたとき、取り消したとき、削除を求めたときに、データを消す仕組みがあるか
9. **年齢**: 生成 AI や酒類など、年齢で制限がかかるものを未成年が使える状態にしていないか
10. **禁止用途**: 負荷試験、存在しない ID への送信、スクレイピング、モデル学習、広告媒体化、なりすまし
11. **鍵と認証**: API キーの制限、署名検証、ID トークンの検証
12. **提供元データ**: 第三者から提供を受けたデータを、生成 AI で加工・外部送信・配信する許諾があるか
13. **計測・監視への混入**: 分析、広告、エラー監視、ログ基盤に、個人情報・秘密情報・他社 API の応答を送っていないか
14. **課金とストア**: 決済の扱い (カード情報、課金手段の指定)、アプリストアの審査ガイドラインとプライバシー申告が実装と一致するか
15. **申告との一致**: プライバシーポリシー、ストアのプライバシー申告、同意画面に書いた内容と、実際に送っているデータが一致するか

## 判定の 4 段階

| 判定 | 使う場面 |
|---|---|
| 違反の疑い (`V`) | 適用される規約の文面と実装が明らかに食い違い、例外に当たる事実も見当たらない |
| 要判断 (`J`) | 事実は分かっているが、規約の読み方、契約の中身、運用次第で結論が変わる。推奨 (should) 止まりの規定も含む |
| 未確認 (`U`) | 判定に要る事実 (コンソール設定、契約、実データ、規約の原文) が手元に無い |
| 適合 (`OK`) | 事実と規約の両方を確認して、沿っていると言える |

4 つは重さの順ではなく、**分かっていることの状態**で選ぶ。証拠が足りなければ `U`、解釈が分かれるなら `J`、確認できたときだけ `OK`。証拠不足を「軽く」して `OK` にしない。観点が当てはまらない (そのサービスに該当する機能が無い) ものは `OK` にせず、メモか `survey.unverified` に「対象外」と書く。

`V` にするのは、例外に当たる事実が無いことまで確かめたときだけ (例: 委託の例外があるなら、委託契約や委託の実態が無いことを確かめる)。確かめられなければ `J` か `U` にして、分かれ目を `clause` か `action` に書く。

影響の大きさ (利用者数、取り返しのつかなさ) は判定とは別に、カテゴリと工数 (Phase 5) で表す。

## finding の書き方

```json
{
  "id": "L-02",
  "service": "line",
  "owner": "LINE",
  "sev": "V",
  "title": "チャット本文を外部の生成 AI に送っている",
  "clause": "LINE ユーザーデータポリシー 1.2 (公式アカウントが受け取ったメッセージは LINE ユーザ情報)、3.4 (第三者開示の禁止。例外は法令と業務委託)",
  "fact": "src/lib/line/consult.ts:186-218 で発話全文と直近 7 件を Gemini に送る。userId と表示名は送らない。委託契約やプライバシーポリシーでの整理は無い (確認済み)",
  "action": "LINE 経由の本文を外に出さない設計にする。...",
  "basis": "規約",
  "refs": ["S-LINE-UDP"],
  "related": ["V-02"]
}
```

- `id`: サービスの頭文字 + 連番 (G-01, L-01, V-01, E-01 など)。後から統合しても番号は振り直さない (外部に共有済みの番号がずれるため)
- `owner`: どの規約の論点か。`service` (どのサービスの話か) と違うことがある。例: 生成 AI にチャット本文を送る件は `service` が生成 AI でも `owner` はチャット基盤
- `clause`: 条番号 + 要旨。原文引用は短く
- `fact`: `file:line` と、何がどう流れるか。推測は「未確認」と書く
- `action`: 何をすれば解消するか。複数案あれば並べ、推奨を書く
- `basis`: 根拠の種類。「規約」「ポリシー」「ガイドライン (推奨)」「ライセンス」「個別契約」「法令」のどれか
- `refs`: 出典 (`sources` の `id`)。判定から原文に辿れるようにする
- `related`: 同じ事実から生じる別の義務の項目 ID

## よくある取り違え

- **「保存していない」の早合点**: DB の列を消しても、送信ログ・イベントログの JSON に同じ値が残っていることがある。保存先を grep し直す
- **「表示先が自社アプリだから可」の早合点**: 規約が許すのは「契約者が所有・管理するアプリ」の中であることが多い。契約主体と運営主体が違う場合 (受託開発、グループ会社) は前提として書く
- **「委託先と整理すれば可」の早合点**: 委託の例外は、委託の実態と契約が要る。文書の書き換えだけで済むと書かない
- **画面や置き場所で判定する**: 「自前の画面で入力させたから可」「自前で動かすから可」のように UI やホスティング形態だけで判定しない。データの由来 (誰から、どのサービス経由で受け取ったか) と受領主体 (誰の管理下に渡るか、その先のクラウドやログ基盤を含む) で判定する
- **「加工すれば対象外」の早合点**: 要約・構造化しても、1 人分の情報から作ったものは元の情報として扱われることが多い。対象外と明記されているのは統計データ程度
- **項目の単位を間違える**: 項目は「同じ義務・同じ適用条件・同じ是正」で 1 つにする。同じ事実でも、別の規約の別の義務 (例: 送り元の第三者提供の制限と、受け手側の入力データの権利・年齢条件) は別項目にし、`related` で結ぶ。片方が適合で片方が未確認、のように状態が分かれ得るため。逆に、同じ義務を言い換えて 2 項目に書くのは統合する
