# 外部サービスの論点

前半は分類ごとの観点 (どのサービスにも当てる)、後半は個別サービスで実際に問題になった論点の控え。個別サービスの節は「どこを見るか」の手がかりで、一般則ではない。**規約は改定されるので、ここは「どこを見るか」の手がかりとしてだけ使い、判定は必ず最新の原文で行う。** 条番号は 2026-10 時点のもの。

## 分類ごとの観点

| 分類 | 主に見ること |
|---|---|
| メッセージング・チャット基盤 | 受け取ったメッセージやユーザー ID の扱い (第三者提供、保存期間の明示、削除)、配信内容の禁止事項、存在しない宛先への送信や負荷試験の禁止、広告利用の制限 |
| 地図・位置情報 | キャッシュできる範囲と期限、派生値の利用、帰属表示 (ロゴ寸法、クレジット)、改変の禁止、他社地図との併用、利用者の位置情報の扱い |
| 生成 AI・機械学習 API | 入れるデータの権利 (他社から受け取ったデータ、個人情報、提供元の文章)、学習利用と保持期間、年齢制限、禁止用途、出力の表示義務の有無、安全フィルタ |
| 決済・課金 | 決済サービスの規約が求めるカード情報の扱い (トークン化、PCI DSS 準拠の求め)、制限業種、デジタル商品の課金手段 (アプリストアの課金規定)、返金・解約の導線。特定商取引法などの法令は依頼があるときだけ、根拠の種類を「法令」として扱う |
| 認証・ソーシャルログイン | 取得するスコープが用途に見合うか、プロフィール情報の保存と更新、ストアが求めるログイン手段 (例: iOS アプリは App Review Guidelines 4.8 の適用対象・同等の代替手段の要件・例外を確認)、退会時の連携解除 |
| メール・SMS・電話 | 送信の同意 (オプトイン) と配信停止の手段、送信者表示、特定電子メール法などの表示、送信内容の禁止事項、宛先リストの出所 |
| プッシュ通知 | 許可の取得、広告目的の通知の扱い (ストアのポリシー)、トークンの保存と削除 |
| 分析・計測・広告 | 個人を特定できる情報を送っていないか (多くの規約が禁止)、同意管理、プライバシーポリシーへの記載、子ども向けアプリでの制限、トラッキングの許可 (ATT など) |
| エラー監視・ログ・APM | 送信する例外やリクエストに個人情報・秘密情報・他社 API の応答が混ざっていないか、保存場所 (国外) と期間 |
| ストレージ・CDN・ホスティング・クラウド | 利用規約の禁止コンテンツ、データの所在地、他社から受け取ったデータを置いてよい場所か (再ホストの禁止との関係)、公開範囲の設定 |
| アプリストア・配布 | 審査ガイドライン (課金、ログイン、データ収集の申告、子ども向け)、プライバシー申告 (App Privacy、データセーフティ) と実装の一致 |
| 外部データ API・オープンデータ・提供データ | ライセンス (商用可否、出典表示、改変可否、再配布)、保存期間、取得頻度の上限、生成 AI での加工の可否、契約終了時の削除 |
| 埋め込み・ウィジェット | 表示の改変禁止、埋め込み先の制限、埋め込みが行う計測のプライバシーポリシーへの記載 |
| スクレイピング先 | 取得そのものを利用規約や robots.txt が禁じていないか、取得したデータの権利、負荷 |

どの分類でも、**他社から受け取ったデータを別の外部サービスに送っていないか** (送り元の規約の論点)、**プライバシーポリシーにサービス名と送る項目を書いているか**、**退会・削除で外部側のデータも消えるか** は共通して確認する。

## 個別サービスで問題になった論点

## LINE (Messaging API / LINE Login / LIFF / 公式アカウント)

- **トークの本文は「LINE ユーザ情報」**: ユーザーデータポリシー 1.2 は「公式アカウントが受領したユーザからのメッセージ」を明示的に例に挙げる。誰が入力したかではなく、LINE サービス内で取得したかで決まる
- **自社サービス内で直接取得した情報は対象外になり得る**: 同 1.2 の但し書き「LINE Login 機能を付加した場合でも、そのサービス内で Developer がユーザから直接取得する情報は LINE ユーザ情報に該当しない」。ただし画面の種類 (LIFF かどうか) ではなく、データの由来で判定する。LINE のプロフィールや ID トークンの情報、トーク由来の情報が混ざれば対象に戻る。送信先側の規約 (年齢条件、データの扱い) と個人情報保護法は別に残る
- **第三者開示の例外は 2 つだけ**: 3.4 (法令、業務委託)。利用者の同意は例外に入っていない。公式アカウント利用規約 8 条 2 項は書面の事前許諾を求める。外部の生成 AI API に本文を送るのは典型的な論点
- **加工しても対象外にならない**: 対象外と明記されているのは「個人を特定できない統計データ」(3.5) だけ。要約・構造化した 1 人分のデータはグレー
- **自己ホストのモデル**: 自社の管理下で動かすモデルに渡すだけなら、3.4 の第三者開示には当たりにくい。ただし、実行基盤のクラウド事業者、ログ基盤、監視 SaaS などに本文が流れる経路があれば、それぞれ別に確認する。目的外利用 (3.2.4) と保存の明示 (3.2.3) は残る
- **24 時間以上の保存は明示が要る**: 3.2.3 の原文は「24時間以上」。ユーザー ID 以外 (本文、画像、表示名) を 24 時間以上残すなら利用者に明示する。友だち情報・グループ情報は明示の有無にかかわらず 24 時間以上保存できない。削除ジョブの間隔や遅延も含めて期限を評価する
- **退会と連動解除は義務**: 3.2.10。LIFF / LINE Login の開発ガイドラインは退会時の認可取消を求める。終了時の削除 (3.5.2) と廃棄証明 (3.5.4)
- **プライバシーポリシーは利用開始前に読めること**: 2.4。オンボーディングのガードの内側に置くと読めない
- **送信取消は削除が推奨**: Messaging API 開発ガイドライン (推奨止まりなので「要判断」)
- **禁止事項**: 存在しないユーザー ID への送信、LINE 経由の負荷試験、第三者のための広告媒体化 (公式アカウント利用規約 18(6))、酒類などの年齢配慮 (公式アカウントガイドライン)
- **自動応答も配信コンテンツ**: フォールバック返信で利用者の入力をそのまま引用すると、公式アカウントの発言として再送される

## Google Maps Platform

**API・フィールド・用途・適用契約ごとに判定する。** Maps Platform の規約は API ごとに例外が多く、ある API の規定を Maps 全体に広げると誤る。以下は Places / Routes / Geocoding / Maps JavaScript を使うアプリで問題になった論点の原則と、確認すべき例外。

| 論点 | 原則 (Terms of Service) | API ごとに確認する例外 (Service Specific Terms ほか) |
|---|---|---|
| 保存・キャッシュ | 3.2.3(a)(iii), (b): Google Maps Content を保存・キャッシュしない | place_id などの Google ID は保存可。Places・Routes の緯度経度は 30 日まで。Geocoding は条件付きで無期限保存の規定 (6.3.2) がある。他の API (Pollen、Air Quality など) は別の期間。使っている API の条項を個別に引く |
| 派生値 | 3.2.3(c): Google Maps Content を基にコンテンツを作らない (例: Places の緯度経度を point-in-polygon 分析の入力に使う) | LLM への投入は Maps Grounding (B.10) などが「限定例外」として用意されている。座標から計算した最寄り駅、半径での絞り込み、プロンプトへの投入は、例外に乗らない限り論点になる。判断に使う座標を Google 以外から作れば論点ごと消える |
| 他社地図との併用 | 3.2.3(e): Google 以外の地図と一緒に使わない | Places UI Kit など、併用を許す API がある。使っている API の条項を確認する |
| 改変 | 3.2.3(g): 検索結果を改変しない (例: Google が返した URL を差し替えて Google 欄に出す) | 非表示は差し替えと同じではない |
| 利用規約への記載 | 3.2.2(a): アプリの利用規約に Google Maps を含むことと、Google Maps 追加利用規約・Google プライバシーポリシーへのリンク | - |
| 帰属表示 | 3.2.2(b) と各 API の Policies ページ: ロゴ・テキストの帰属、写真の著者帰属 | ロゴの寸法、省略してよい条件 (サムネイルなど) は API の Policies ページで確認する |
| 表示できる場所 | ライセンスは Customer Application の中で使うもの | 契約主体と運営主体が違う (受託開発、グループ会社) ときは、そのアプリを契約主体の Customer Application と言えるかを前提として書く |

期限付きの保存は、「期限を超えて使わない」だけでなく「期限内に削除する」ことまで確認する。ジョブの停止時とバックアップの扱いも見る。

## Google の生成 AI (Vertex AI と Gemini Developer API を分ける)

**まず、どの入口で使っているかを特定する。** Vertex AI (Google Cloud の規約) と Gemini Developer API (Google AI Studio、Gemini API 追加利用規約) では、データの扱いが別の規約で決まる。Developer API は無料扱いか有料扱いか、利用地域によって、入力・出力をサービス改善に使うかどうかが分かれる。エンドポイント (`aiplatform.googleapis.com` か `generativelanguage.googleapis.com` か)、課金状態、モデル、使っている機能 (Grounding など)、地域を台帳に書いてから判定する。

- **年齢**: Google Cloud Service Specific Terms の生成 AI の章に、18 歳未満が対象または利用する見込みのあるサービスで使ってはならない旨がある (2026-10 時点)。Developer API 側の年齢条件も別に確認する
- **データの保持と学習利用**: 「学習に使われない」は入口と課金状態に依存する。Vertex AI でも、キャッシュや不正利用監視のための保持の規定がある。期間は公式の最新ドキュメントで確認し、出典を付ける。「学習に使われない」を「保存されない」と書かない
- **出力の使い方**: 生成結果をアプリで表示・配信すること自体は通常の使い方だが、禁止用途ポリシー、出力を使った競合モデル開発の制限、Grounding 機能を使う場合の表示・保存条件などが付く。「自由」と書かない
- **安全フィルタ**: 設定は顧客側の責任。外したバッチは補償の条件に影響し得る
- **入れるデータの権利**: 提供元の文章や他社のユーザーデータを入れる権利は顧客側の責任。送り元の規約が先に問題になることが多い

## 他の生成 AI API (OpenAI、Anthropic など)

- データの保持期間とゼロ保持の条件、学習利用の有無、年齢条件、禁止用途を、Google と同じ観点で確認する
- 他社プラットフォーム (チャット基盤など) から受け取ったデータを送るなら、送り元の規約が先に問題になる

## データ提供元 (公開規約が無いもの)

- 生成 AI での加工、要約、外部送信、チャットでの配信、画像の保存が、個別契約で許されているか
- クレジット表記の全文表示義務 (省略で末尾の権利者名が消える)
- 「原文のまま載せない」約束がある場合、書き直し未処理の行が原文のまま出る経路が無いか
- 無料 API のデータを同梱・再配布していないか
