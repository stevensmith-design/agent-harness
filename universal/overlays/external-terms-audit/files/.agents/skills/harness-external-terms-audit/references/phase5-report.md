# Phase 5: 整理して描く

読み手は「どこが危なくて、何をすれば良いか」を最初の 1 画面で知りたい。レポートは次の順で組む (`render.py` がこの順で描く)。

1. **経路ごとの流れと該当項目 (具体例)**: 一覧表 (経路 x 規約) と、経路ごとの縦のフロー
2. **対応方針 (カテゴリ A-F)**: 対応の種類と工数で分けた一覧
3. **サービス別の項目**: findings の全件
4. **コードの外で確認が要ること**
5. **独立レビューとの照合**
6. **参照した規約**
7. **付録: 依頼者の疑問への回答**
8. (Phase 1 の成果があれば) **システム概要と構成図** を冒頭に置く

## 1. 経路ごとの具体例 (`flows`)

Phase 1 で洗った経路ごとに、1 本の具体的な操作 (架空の発話、架空の店名) を通して、各ステップで動くデータを実物の形で載せる。

- ステップの `actor` は境界を表す。既定は `platform` (チャット基盤など外部プラットフォーム側)、`app` (自社の実行環境と DB)、`vendor` (外部の API・生成 AI)、`source` (データ提供元)。`report.json` の `actors` で名前と色を変えられる
- `data` には JSON、SQL の列、プロンプトの抜粋を 1 行ずつ。注目させたい値は `{{...}}` で囲むと強調される。行末の注記は `  <- ` で始めると薄い色になる
- `items` には、そのステップで関わる項目を `[文, [ID, ...]]` で。チップは判定の色 (違反は赤) で描かれる
- 一覧表 (経路 x 規約) は flows の ID と各 finding の `owner` から自動で作られる

## 2. 対応方針 (`categories`)

違反の疑い・要判断・未確認の全項目を、ちょうど 1 つのカテゴリに入れる (`--check` で漏れと重複を検出)。既定のカテゴリ:

| コード | 中身 | 工数 |
|---|---|---|
| A | 利用規約・プライバシーポリシーの変更だけで済む | 小 |
| B | 年齢などの利用条件のチェックを入れれば済む | 小 |
| C | レスポンスの仕方を変えれば済む (ロジック変更) | 中 |
| D | 機能を実装すれば済む (退会、削除、保持期間) | 中 |
| E | システムの設計から見直す | 大 |
| F | その他 (契約・設定・相手先の確認で決まる) | 確認待ち |

カテゴリや工数の区分は依頼者の希望に合わせて変えてよい。`policy` は短い箇条書き (1 行 1 文) にし、論点が複数ある場合は `{"text": 親, "children": [子, ...]}` で親子にする。設計の選択肢は「(1-1) (1-2) ... 推奨: ...」の形で並べる。

## 3. 書き方

- 1 文 1 論点。長い段落にしない
- 推奨を書く。選択肢だけ並べて終わらない
- 依頼者が却下した案や、採らない理由の長い説明は書かない
- 「違反」は「違反の疑い」と書く (法的判断ではないため)。チップは短く `[違反] L-04`
- 独立レビューを行わなかった場合は、`meta.lead` と `cross_review.reviewer` にその旨を書く
- 店名、発話、ID などの例は架空にする。実データの個人情報を載せない

## 4. 描く

```bash
python3 <skill>/scripts/render.py <出力先>/report.json --check
python3 <skill>/scripts/render.py <出力先>/report.json --format both --out <出力先>
```

HTML はヘッドレス Chrome でスクリーンショットを撮って確認できる。

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu \
  --hide-scrollbars --window-size=1100,4000 --screenshot=<出力先>/shot.png "file://<出力先の絶対パス>/report.html"
```
